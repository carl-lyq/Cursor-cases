# Cursor 案例库 · 产品需求文档（PRD）

> **版本**：v1.3  
> **更新日期**：2026-06-23  
> **状态**：已落地 MVP，持续迭代  
> **文档定位**：本文件是 Cursor 案例库的**唯一产品真相来源**。产品、运营、研发、测试均以本文为准；技术实现细节见 `docs/01-架构说明.md` 等配套文档。

---

## 1. 项目背景

团队在 `AI Projects` 工作区下并行推进多个业务项目，并大量使用 Cursor Agent 协作。每个项目里「用 AI 提效」的方式、收益、突破点分散在各自仓库、对话记录和参与者记忆中，**缺少一份跨项目、可对外汇报的统一案例材料**。

以往若要整理案例，需要专人逐个翻项目、问同事、手写 PPT 或文档，耗时长、口径不一、难以及时更新，也无法系统回答三个核心问题：

1. 这个项目**如何通过 AI 提效**？
2. 比**传统工作流**快在哪里？
3. 有哪些事是**以前做不到、现在可以**的？

Cursor 案例库旨在用**半自动采集 + 人工确认**的方式，持续产出上述问题的答案，服务内部分享、汇报与经验沉淀。

## 2. 产品定位

| 维度 | 说明 |
|------|------|
| **是什么** | 跨项目 Cursor 提效案例的**采集、整理、确认、发布**工作台 |
| **不是什么** | 不是技术日志仓库、不是项目管理工具、不是躺着学 AI 项目库的替代品 |
| **核心价值** | 把分散的协作痕迹变成**同事可读**的汇报材料，且**发布前必经人工把关** |
| **使用场景** | 周会/月会案例分享、管理层汇报、团队复盘、新人了解「我们怎么用 Cursor」 |

与 **躺着学 AI 项目库** 的关系：**完全独立**。本仓库自洽运行；未来若需对外展示，可再将 `published/` 内容导入其他 Portal，本期不做打通。

## 3. 目标用户

| 角色 | 诉求 | 主要使用方式 |
|------|------|--------------|
| **案例维护者（Owner）** | 保持案例库新鲜、准确，控制对外口径 | 触发扫描、阅读待确认清单、确认发布、补充事实卡片 |
| **汇报者** | 快速拿到可信的正式版材料 | 阅读 `published/AI-Projects-Portfolio.md` 与单项目案例卡 |
| **产品 / 运营 / 研发同事** | 了解其他项目如何用 Cursor，借鉴做法 | 阅读已发布案例卡 |
| **管理层** | 纵览 AI 提效成果，少技术黑话 | 阅读正式总览与重点案例的「变化 / 突破」章节 |

## 4. 问题与痛点

| 痛点 | 现状 | 本产品如何解决 |
|------|------|----------------|
| 信息分散 | 收益写在对话、PRD、脑子里 | 自动从仓库与 Agent 对话采集，汇总到统一目录 |
| 整理成本高 | 人工逐个写案例，动辄数天 | 自动生成约 70% 可用初稿，人只负责核实与润色 |
| 口径不可控 | 自动文本易夸大或含敏感信息 | **确认后才发布**；支持定稿锁定 |
| 更新滞后 | 做完项目忘了补案例 | 每日云端自动扫仓库；本机补扫对话 |
| 读者难懂 | 技术日志不适合汇报 | 案例卡强制业务语言结构，证据下沉到 `inbox/` |

## 5. 产品目标与成功标准

### 5.1 目标

1. **全覆盖**：`AI Projects` 下活跃子项目均有案例卡（可标记忽略测试项）。
2. **可读性**：非技术同事无需读代码即可理解「以前怎么做 → 用 Cursor 后 → 带来什么变化」。
3. **可信性**：对外材料均经 Owner 确认；量化数据有来源或已人工核实。
4. **可持续**：无需每天手工维护；自动草稿 + 定期确认即可保持更新。

### 5.2 成功标准（可观测）

| 指标 | 期望 |
|------|------|
| 项目覆盖率 | 活跃项目 ≥ 90% 有案例卡（`ignored` 除外） |
| 确认周期 | 自动扫描后 7 日内完成待确认项处理（或明确忽略） |
| 正式版可用性 | `published/` 可直接用于汇报，无需二次大改 |
| 自动化运行 | 每日云端扫描正常执行；本机每周至少一次全量扫描 |

## 6. 范围界定

### 6.1 本期范围（MVP，已落地）

- 跨项目自动扫描（仓库文档 + Git 信号 + 本机 Agent 对话）
- 案例卡与草稿总览自动生成
- 待确认清单（`reviews/LATEST.md`）
- 对话 / 命令行确认发布
- GitHub 每日自动扫描（仓库部分）
- 案例状态管理（draft / confirmed / locked / ignored）
- 子项目可选事实卡片（`ai-impact.yaml`）

### 6.2 暂缓（文档已预留，未实现）

| 能力 | 说明 |
|------|------|
| 飞书通知 | 扫描完成后推送「待确认」提醒，见 `docs/05-飞书通知（待接入）.md` |
| 手机端操作 | 无完整手机 IDE；Cloud Agent 监督本期不纳入案例库流程 |

### 6.3 明确不做

- 替代各子项目自身的 PRD / 项目管理
- 自动未经确认写入 `published/`
- 在通知或案例正文中暴露敏感业务数据、密钥、客户隐私
- 本期与躺着学 AI 项目库双向同步

## 7. 核心概念

### 7.1 事实层 vs 叙事层

| 层次 | 内容 | 来源 |
|------|------|------|
| **事实层** | 项目背景、传统流程、Cursor 用法、耗时、产出物 | 结构化采集（yaml、PRD、README、对话、Git） |
| **叙事层** | 「比以前快在哪」「以前做不到什么」 | 自动初稿 + **人工确认润色** |

**原则：机器只写草稿，叙事对外发布必须经人确认。**

### 7.2 双引擎采集

| 引擎 | 运行环境 | 采集内容 | 电脑关机时 |
|------|----------|----------|------------|
| **仓库引擎** | GitHub Actions（每日 09:00） | 子项目 PRD/README、Git 历史、`ai-impact.yaml` | ✅ 云端照常 |
| **对话引擎** | 本机 Mac（建议每日 08:15） | `~/.cursor/projects` 下 Agent 对话 → **脱敏摘要** | ❌ 延后；云端读上次推送的 digest |

**对话不入库原文**：本机全量 `scan` 经 `lib/sanitize` 过滤邮箱、手机、密钥、本机路径等，仅将摘要写入 `state/session-digests.json` 并推送到 `portfolio-draft`。云端 `--repo-only` **不读 transcript**，只读已推送的 digest，用于案例卡「近期协作摘要」。

本机执行「全量扫描」= 仓库引擎 + 对话引擎。关机不丢仓库侧更新；对话摘要可能晚一天，待确认清单会标注是否含积压补扫。详见 [07-本机每日对话同步.md](./07-本机每日对话同步.md)。

### 7.3 草稿与正式版

| 产物 | 目录 | 谁可对外使用 |
|------|------|--------------|
| 草稿总览 | `draft/` | ❌ 仅内部参考 |
| 正式总览 | `published/` | ✅ 汇报首选 |
| 案例卡 | `cases/` | draft 状态仅内部；confirmed 后纳入正式总览 |
| 待确认清单 | `reviews/` | Owner 工作队列 |
| 机器证据 | `inbox/` | 不对外，供核实与追溯 |

## 8. 功能需求

### 8.1 扫描与采集

| ID | 需求 | 优先级 | 验收标准 |
|----|------|--------|----------|
| F-01 | 识别 `AI Projects` 下子项目并生成/更新案例卡 | P0 | 每个非 ignored 项目有对应 `cases/<id>.md` |
| F-02 | 读取子项目 PRD、README 作为背景来源 | P0 | 案例卡「背景」节有内容或明确待补充 |
| F-03 | 读取子项目 `.cursor/ai-impact.yaml` 并优先采用 | P1 | yaml 中字段覆盖自动推断 |
| F-04 | 采集本机 Agent 对话并关联到项目 | P0 | 脱敏摘要写入 `session-digests.json`，并反映到案例卡「近期协作摘要」 |
| F-05 | 每日云端自动执行仓库扫描 | P0 | GitHub Action 按时触发并更新 draft 相关目录 |
| F-06 | 支持仅扫仓库 / 仅补对话 / 全量三种模式 | P1 | 命令行参数可用，见使用手册 |
| F-07 | 关机或离线后对话积压可追平 | P1 | 下次全量扫描后 `reviews` 标注积压 |
| F-17 | 对话与案例中的敏感信息自动过滤 | P0 | 不推送 raw transcript；邮箱/手机/密钥/本机路径等脱敏；敏感任务整段跳过 |

### 8.2 合成与呈现

| ID | 需求 | 优先级 | 验收标准 |
|----|------|--------|----------|

| F-10 | 每次扫描生成待确认清单 `reviews/LATEST.md` | P0 | 列出新增/更新项与操作建议 |

## 9. 案例内容规范

每张案例卡须面向**非技术读者**，章节顺序固定，**每节须有具体业务信息**，禁止空泛套话。

| 章节 | 要求 |
|------|------|
| **业务背景** | 谁在用、典型场景、业务问题与要解决什么（`users` / `scenario` / `background` / `solution`） |
| **工作痛点** | 3–6 条业务痛点；可含传统方式耗时基线 |
| **项目要做什么** | 业务交付视角：先一句目标，再分输入/产出/能力 |
| **工作方式对比** | **传统方式** vs **用 Cursor 之后**（步骤化描述） |
| **提效与业务价值** | 对比表（耗时/质量）+ 谁受益 + 效率/质量/新突破 |
| **Cursor / AI 能力与工具** | 能力、工具、Skills 分块列出 |
| **近期协作摘要**（有对话时） | 按日期列出：任务描述、结果摘要、涉及文件 |
| **仓库活跃信号**（有 Git 时） | 提交次数、近期方向、产出类型分布 |
| **元信息** | 项目路径、状态、文档来源、生成日期 |

**信息来源优先级**：`ai-impact.yaml` > 项目 PRD（含 `*PRD*.md`）> README > Agent 对话 > Git 信号。

**语气**：像对内汇报稿，不像 commit log。  
**数字**：自动推断的数字在待确认清单中标记「待核实」；确认前须核对或删减。  
**敏感信息**：入库前经自动脱敏（见 F-17）；确认发布前仍须人工检查无内部机密、客户隐私、未公开数据。

子项目维护者可通过 `.cursor/ai-impact.yaml` 主动提供高质量事实（模板见 `templates/ai-impact.example.yaml`），减少自动推断误差。

## 10. 用户路径

### 10.1 日常维护者路径

```
每日云端自动扫仓库（无需操作）
        ↓
完成重要协作后 / 每周 → 本机全量 scan
        ↓
打开 reviews/LATEST.md → 查看新增/更新/待核实
        ↓
阅读 cases/*.md → 核对事实，必要时改 ai-impact.yaml 或标 locked/ignored
        ↓
对话「确认 portfolio」或 CLI confirm → 发布正式版
        ↓
汇报者使用 published/AI-Projects-Portfolio.md
```

### 10.2 出差 / 关机回来路径

```
GitHub 每日 Action 已更新仓库部分草稿
        ↓
本机 git pull → scan（或 scan --transcripts-only 仅补对话）
        ↓
reviews 若标注「积压补扫」→ 优先处理对应对话相关更新
        ↓
确认发布
```

### 10.3 汇报者路径

```
打开 published/AI-Projects-Portfolio.md
        ↓
按目录进入重点 cases/*.md
        ↓
直接用于会议 / 文档 / 幻灯片素材（无需读 draft 或 inbox）
```

### 10.4 子项目贡献者路径（可选）

```
在子项目新增 .cursor/ai-impact.yaml
        ↓
填写 traditional / with_cursor / impact
        ↓
下次案例库 scan 自动吸收 → Owner 确认后进入正式版
```

## 11. 状态与交互规则

### 11.1 案例状态机

```
        ┌──────────┐
        │  (新建)   │
        └────┬─────┘
             ▼
        ┌──────────┐     确认发布      ┌────────────┐
        │  draft   │ ───────────────► │ confirmed  │
        └────┬─────┘                  └─────┬──────┘
             │                              │
      标 ignored                      标 locked
             │                              │
             ▼                              ▼
        ┌──────────┐                  ┌────────────┐
        │ ignored  │                  │  locked    │
        └──────────┘                  └────────────┘
```

| 状态 | 含义 | 自动扫描行为 | 是否进入 published |
|------|------|--------------|-------------------|
| `draft` | 自动草稿，待确认 | 可更新正文 | 否 |
| `confirmed` | 已发布 | 可更新（除非 locked） | 是 |
| `locked` | 汇报定稿 | **不覆盖**案例正文 | 是 |
| `ignored` | 不纳入案例库 | 跳过 | 否 |

### 11.2 确认交互

| 入口 | 用户说法 / 操作 | 系统行为 |
|------|-----------------|----------|
| Cursor 对话 | `确认 portfolio` | 确认全部待发布项 → 更新 published → push main |
| Cursor 对话 | `确认 portfolio <项目名>` | 仅确认指定项目 |
| 命令行 | `portfolio.py confirm [--cases ...]` | 同上 |

确认前检查清单（产品要求，非可选项）：

- [ ] 已阅读 `reviews/LATEST.md`
- [ ] 「待核实」数字已核对或删减
- [ ] 无敏感信息，语气适合对外
- [ ] 项目名称与背景准确

详见 `docs/03-确认发布流程.md`。

## 12. 自动化节奏

| 时机 | 行为 | 执行方 |
|------|------|--------|
| 每天 08:15（北京时间，建议） | 本机全量 `scan` + 推送脱敏 digest | Mac `daily-local-sync.sh`（见 [07](./07-本机每日对话同步.md)） |
| 每天 09:00（北京时间） | 仓库扫描，合并 digest 更新案例卡 | GitHub Actions |
| 完成重要协作后 | 建议本机全量 `scan` | Owner |
| 出差 / 长时间关机后 | `scan` 或 `scan --transcripts-only` | Owner |
| 汇报前 | 读 `reviews/LATEST.md` 并确认 | Owner |

**产品预期**：电脑关机时仓库侧仍每日刷新；对话摘要用上次本机推送的 digest（可能晚一天）；下次本机扫描追平积压。

## 14. 质量保障

| 机制 | 说明 |
|------|------|
| 人工确认闸门 | 唯一写入 `published/` 的路径 |
| 待核实标记 | 自动推断的量化数据须在确认前处理 |
| ai-impact.yaml | 子项目主动提供事实，提高准确率 |
| locked | 已定稿案例防静默覆盖 |
| ignored | 测试/废弃项目不污染案例库 |
| 业务语言模板 | 统一章节，降低「技术日志感」 |

## 15. 非功能需求（产品侧）

| 类别 | 要求 |
|------|------|
| **可用性** | Owner 无需读代码即可完成 scan → review → confirm |
| **可追溯** | 扫描时间、模式、证据保留在 `inbox/` 与 `reviews/` |
| **安全** | Webhook 等密钥不进仓库；对外文稿不含敏感数据 |
| **独立性** | 单仓库可 clone 即用，不依赖躺着学 AI 项目库 |
| **可维护性** | 规则写入 `.cursor/rules/`，对话可触发确认流 |
